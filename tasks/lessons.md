# Lessons — Project-Specific Pitfalls

## L1 — Never assume an external API returns an array.
**Rule:** When integrating a community/free API, do NOT write `return data?.SOMEKEY || []` and feed it to `for...of`. Inspect the real shape first with a `console.log("RAW X DATA:", data)`, then write defensive extraction that handles: top-level array, nested array under a key, nested object under a key (use `Object.values()`), and total garbage.
**Why:** Sprint 4.5 Amtraker call crashed with `TypeError: trains is not iterable` because `data.ALB` came back as an object keyed by trainId, not an array. The fetcher returned the object straight to a `for...of` loop and 500'd the whole dispatch.
**How to apply:** Every external fetcher must (1) inspector-log the raw response on first build, (2) extract via Array.isArray → key-as-array → key-as-object via Object.values → top-level Object.values, (3) wrap the extraction in try/catch with a `return []` fallback, (4) guarantee the return type is always an array. Add an `Array.isArray` guard at the top of any consumer that loops over the result.

## L3 — Next.js App Router caches `fetch()` by default.
**Rule:** Every `fetch()` to a live external API inside an App Router route handler (`app/api/**/route.js`) MUST pass `{ cache: "no-store" }`. Default behavior is `force-cache`, which silently serves stale data forever.
**Why:** Sprint V2 follow-up: AviationStack arrivals + Ticketmaster events + weather + trains were all being served from Next.js's fetch cache, so the LLM kept getting hours-old (or days-old) data even though the API itself returns live results. The dispatch payload looked fine; the data inside was just frozen.
**How to apply:** When adding any new external fetcher in a route handler, set `cache: "no-store"` in the fetch options object from the start. If the fetcher already has options like `{ signal }`, add `cache: "no-store"` alongside — don't replace the object. Static/build-time data is the only exception, and dispatch has none.

## L4 — Never use unescaped backticks inside a backtick template literal.
**Rule:** Inside `buildSystemPrompt`'s template-literal return (or any other ``` ` ` ```-delimited string), do NOT use backticks for inline-code formatting (e.g., `` `localDensity` ``). The inner backtick silently closes the outer template literal, turning the next identifier into a parse error like `Unexpected identifier 'localDensity'`. Use double quotes, single quotes, or escape with `` \` `` instead.
**Why:** Sprint 12 introduced `` `localDensity` `` as inline-code emphasis inside the system prompt's template literal. Next.js reported "Failed to Compile" because the prompt's outer template ended at the first inner backtick, then JS tried to evaluate `localDensity` as an identifier in expression position. `node --check` did not catch it (it only validates top-level syntax, not deep nested parsing of the parsed template segments in this case) but `node -e "import(...)"` surfaced it as `Unexpected identifier 'localDensity'`.
**How to apply:** When adding emphasis around a field/variable name inside the system-prompt template, write `"localDensity"` or `'localDensity'`, never `` `localDensity` ``. If a real backtick is needed in the prompt text, escape it: `` \` ``. After any non-trivial edit to `buildSystemPrompt`, run `node -e "import('file:///.../route.js')"` (not just `node --check`) to confirm the module fully parses.

## L5 — Prompt-only rules lose to "data obligation" when the raw data signal is strong.
**Rule:** Telling the LLM "do not route to X" in the system prompt is NOT sufficient when X is still richly present in the payload (e.g., `"15 Arrivals (from MCO, ORD, ATL)"`). The model feels obligated to use the data and will violate the prompt rule. Sanitize at the data layer too — either wipe the field, or overwrite raw values with a synthetic instruction that already encodes the desired behavior.
**Why:** Sprint 10's "CRITICAL — ACTIVE PLATFORMS" prompt block failed → had to add Sprint 11 payload sanitization. Same pattern repeated in Sprint 15: the "CRITICAL GEOGRAPHIC RULE" forbidding ALB dispatch was bypassed by the LLM because `flightsByHour` still showed a 15-arrival surge — the model assumed the data was there for a reason and routed to ALB anyway. Fixed by Synthetic Data Swap: keep the time bucket, replace the raw arrival string with `"Secondary Ripple Demand: ... Route driver to downtown hotels ... DO NOT mention ALB."`.
**How to apply:** When adding a guardrail that says "ignore / forbid / do not use" some field in the payload, pair it with a sanitization step. Either (a) wipe the field entirely if the AI doesn't need the timing/structure, or (b) overwrite the value with a synthetic string that encodes the behavior you want (lets the AI keep the timing signal without seeing the tempting raw data). Treat the prompt rule as belt; the data sanitization as suspenders. Both ship together, not one-then-the-other.

## L6 — Never leave `output: 'export'` enabled when pushing backend API routes to Netlify.
**Rule:** `output: 'export'` in `next.config.mjs` forces a static HTML export and strips ALL dynamic API routes (`app/api/**/route.js`). Netlify deploys the static shell; the frontend's `fetch('/api/dispatch')` then hits the 404 HTML page → `Unexpected token '<', "<!DOCTYPE "... is not valid JSON`.
**Why:** Added `output: 'export'` while building the Capacitor native shell (which needs a static bundle), then deployed to Netlify without reverting. The serverless function was never created on Netlify, so the live URL had no backend at all.
**How to apply:** When working in the Capacitor + Netlify cloud-split, NEVER ship `output: 'export'` to Netlify. If a static export is needed for the Capacitor build, run it as a separate one-shot build with the flag enabled, then revert `next.config.mjs` before `git push`. Before any Netlify deploy, confirm `next.config.mjs` is `const nextConfig = {}` (no `output` key). If the deployed site ever returns HTML for a `/api/*` call, check this config first.

## L7 — When user says "Components," do not auto-scope to refactoring the input form.
**Rule:** When the user mentions "components" or "scalable" for this project, the default goal is rendering the backend `itinerary` array as UI cards (FlightCard / TrainCard / HotspotCard), NOT splitting up existing form controls. The form in `app/page.js` is intentionally a monolith and should be left alone unless the user explicitly asks to refactor it.
**Why:** Sprint 24 — I planned to extract HoursSelect/PlatformsToggle/LocationToggle/StrategySelect/DispatchButton from `page.js`. User corrected: the actual goal was replacing the `<pre>{plan}</pre>` text block with mapped cards driven by Sprint 23's `itinerary` array. Sprint 23 already noted "Do NOT build React UI timeline cards yet" — Sprint 24 is when that work happens.
**How to apply:** Before planning any UI work in this project, locate the most recent backend payload (Sprint 23's `itinerary`) and assume the next UI sprint is about rendering it. If "components" is ambiguous, ask: "do you mean rendering the itinerary as cards, or refactoring existing controls?" Default to the former.

## L2 — Mirror the working pattern exactly when adding a new data stream.
**Rule:** When adding a fourth/fifth/Nth live data source, copy the structure of the existing one (fetcher → aggregator → summarizer → Promise.all slot → mergedPayload key → SYSTEM_PROMPT block → userMessage line in BOTH STATE A and STATE B). Don't invent a new shape.
**Why:** Sprint 4.5 trains slot-in worked first try because it mirrored Sprint 4 flights line-for-line. Deviating would have created two divergent patterns and forced the LLM to learn two prompt formats.
**How to apply:** When the user says "add another live feed like the flight one," literally diff the flight code and replicate it with the new domain's specifics.

## L9 — A locked "no new React state" decision must distinguish ticking-timer state from payload-field state.
**Rule:** When writing Sprint Decisions, never write a blanket "no new React state" if the sprint adds a new backend field that the UI must render conditionally. Be specific: "no `useEffect` / `setInterval` / `Date.now()` for the banner" is the real constraint. A one-shot `useState(null)` populated from the dispatch response is the right pattern (mirrors `weatherModifiers`).
**Why:** Sprint 66 locked "no new React state — thread the payload through the existing `itinerary` setter." Halfway through implementation, threading the peak object through an array-typed setter would have forced an object overload and polluted every downstream consumer (`flatItinerary`, `filteredItinerary`, `topPick`). The decision had to be revised mid-sprint and logged.
**How to apply:** When a sprint ships a new backend payload field for the UI, the Decisions section lists `useState` as the source of truth for that field upfront (one line: "`peakSurgeWindow` held in a single `useState(null)`, mirrors `weatherModifiers`"). The anti-goal should target ticking timers explicitly — not all React state.

## L8 — Write the Sprint plan into `tasks/todo.md` BEFORE the first edit.
**Rule:** Every Sprint Master Prompt is a multi-step task per CLAUDE.md § 1 ("Plan First (tasks/todo.md)"). Open `tasks/todo.md` and write a Sprint section with Decisions / Build Steps (checkbox list) / Acceptance Criteria / Anti-Goals BEFORE the first Write or Edit tool call. Check off `[x]` items as each step lands. Retroactive logging after the fact is salvageable but breaks the "paper trail" the rule exists to enforce.
**Why:** Sprints 56 AND 57 were both implemented end-to-end without a single line in `tasks/todo.md` until the user asked "did you write sprint 57 in todo.md file." The codebase shipped fine, but the project's own rule was silently bypassed twice in a row — the kind of drift the file is supposed to catch.
**How to apply:** When a Sprint Master Prompt arrives, the FIRST tool call after planning must be an Edit to `tasks/todo.md` appending the Sprint section. Only after that does the first implementation edit happen. If steps are discovered mid-sprint, edit `tasks/todo.md` again to add them — don't carry them only in TodoWrite (which is conversation-scoped and disappears when the chat ends).
